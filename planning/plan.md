# Implementation plan from the reviewed spec

## Choices

- **Runtime:** Python 3.10+ and the standard library, preserving the existing application and avoiding dependency installation for offline checks.
- **Interface:** a CLI with shared local SQLite state on one host; the user approved this existing design and intake transaction order as the rule for concurrent differing revisions.
- **Test command:** `env -u API_KEY python3 -m unittest discover -s tests -v`, using saved replies, fake HTTP and isolated temporary state so every step is verifiable without a real credential or network.
- **Provider:** a configurable HTTPS adapter to the OpenAI Responses API, with saved-mock mode for reproducible development; plan the existing example configuration (`gpt-4.1-mini`, strict JSON Schema output, max_output_tokens=3000) and check its request contract using fake HTTP. Live availability and quality remain outside offline verification.

These are implementation choices, not new source requirements. This repository already contains code and tests: this document plans their review/refinement and any missing checks. It does not claim a fresh implementation or retrospective test-first history. No code or tests are written in this planning task.

## Steps, in build order

For a new component, write its owned test first, observe a meaningful failure, then implement it. For existing behavior, first inspect and run the test; if coverage is incomplete, add the missing assertion before repairing the behavior and record the actual result. Never delete working code or claim a failure that was not observed. Tests listed here are planned ownership; new test names are proposals, not files/methods claimed to exist. Every test is owned by exactly one step and appears in the test plan. Named tests are planned methods in `tests/test_intake.py`, except the three explicitly retained starter methods in `tests/test_starter.py` (T54–T56); a name already present there may need stronger assertions. No test method is added or executed during this planning task. The first mock test must exercise the mock directly, without depending on validation, routing or storage from later steps. Step 3 ledger tests use the mock adapter and directly persist prepared valid results to test revisions/history; they must not depend on the worker or router added in steps 4–5. Their source-derived Q assertions check the prepared stored record; computation of Q is verified in step 4. ### Exact input and mock conventions

`S01`–`S20` below name the supplied files IT-001.json–IT-020.json; `S21` is examples/requests/SYN-001.json. Each row contains all 12 expected scalar fields, exact routing and issue/evidence expectations, with the source message quoted beside them. A later test referencing S01 inherits that entire field object, not just its highlighted fields. Expected values were reviewed from source messages/policy; no application output is used as truth.

Every automated test runs with live network access blocked and real API_KEY absent. Provider/CLI tests inject saved replies, deterministic delays or fake HTTP errors; credentials tests patch the lookup with a local sentinel. Tests of validation, storage or documentation either consume the saved mock response or make no model call. A document inspection is not made to call a model unnecessarily. Test-generated variants and chosen timing/worker settings are verification inputs, not invented business requirements. Only the plan is written at this stage; test methods, fixtures and observations described below are planned work.
